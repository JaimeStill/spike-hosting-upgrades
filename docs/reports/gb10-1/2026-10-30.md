**Context per session, and concurrent sessions (the architect's questions).**

- **Per session today: 8,192 tokens.** **Estimate**, from
  [llama-context.cpp@b11669](https://raw.githubusercontent.com/ggml-org/llama.cpp/b11669/src/llama-context.cpp)
  (primary, read 2026-10-30): with the KV cache split, `cparams.n_ctx_seq = cparams.n_ctx /
  cparams.n_seq_max`. Both agent sections give 32768 / 4 = 131072 / 16 = 8,192.
  - gpt-oss-120b's trained context is `"max_position_embeddings": 131072`
    ([config.json](https://huggingface.co/openai/gpt-oss-120b/raw/main/config.json), primary,
    read 2026-10-30).
  - So each agent session gets one-sixteenth of what the model can hold. That works against the
    agent purpose, whose sessions carry long tool transcripts.
  - (framework's set-a section avoids this with `--kv-unified`; this host's preset doesn't.)
- **KV per token: 36 KiB.** **Estimate** by the models.md method, from the config above: 36
  layers in alternating `sliding_attention` and `full_attention` (18 of each), 8 KV heads, head
  dim 64, `"sliding_window": 128`.
  - Only the 18 full-attention layers grow with context: 18 × 2 × 8 × 64 × 2 B = 36,864 B per
    token.
  - A full 131,072-token session holds **4.5 GiB**.
  - The sliding layers hold about 128 + 512 tokens per sequence, under 0.4 GiB at 16 slots.
- **Sessions the pool supports with the set loaded: 4 at full context.** **Estimate**, by the
  memory method under "Model set": the recommended set leaves about **20 GiB** for gpt-oss-120b's
  KV and compute buffer within the policy's headroom.
  - At 4.5 GiB per full session, **4** fit (18.0 GiB KV).
  - Or about 8 sessions that average 64K, or 16 that average 32K, sharing one unified pool of
    524,288 tokens.
- **Throughput by concurrency.** These are measured on GB10 by ggml-org at build 7941
  (`llama-batched-bench ... -npp 4096,8192 -ntg 32 -npl 1,2,4,8,16,32`), S_TG t/s at npp 4096
  ([benches/dgx-spark/dgx-spark.md](https://github.com/ggml-org/llama.cpp/blob/master/benches/dgx-spark/dgx-spark.md),
  attributed benchmark by the architect's ruling, read 2026-10-30):

  | Streams | Total decode | Per stream |
  |---|---|---|
  | 1 | 55.21 | 55.2 |
  | 4 | 90.72 | 22.7 |
  | 8 | 139.07 | 17.4 |
  | 16 | 196.26 | 12.3 |
  | 32 | 262.20 | 8.2 |

  The per-stream column is the total divided by the stream count. Build 7941 is about 3,700
  builds before the host's, so the curve shows the shape, not today's figures.

  **The run's reading:**
  - Interactive agent sessions want per-stream speed, which halves by 4 streams and falls by
    three-quarters by 16.
  - The memory limits full-context sessions to 4 in any case.
  - So the pool fits **4 slots at full context**. Measure 8 slots on a shared pool if most
    sessions stay under 64K.

### The conclusion

The most effective engine platform to date for gb10-1 is **the incumbent: llama.cpp's CUDA
router**, in ggml's published image. No other engine has an attributed measurement ahead of it on
GB10. The architect's earlier sessions chose it (Pauses, 2), though those findings aren't listed
in the descriptor (see "Proposed changes").

**Verify**

1. **Image `server-cuda13-b11669` → `server-cuda13-b12004`.**
   - **Sources:** #31188 (+17.2% prefill, MoE Q4_K_M) and #29948 (+7.1% prefill, dense
     Q4_K_M), both attributed on GB10.
   - **Regressions:** none reported after b11669.
   - **Risk:** no root. The rollback is the previous image tag.
   - It goes through spike-model-engines' `engines` suite with anchors A and B.

**Hold**

2. **The agent section: one section, `-c 524288 --parallel 4 --kv-unified`, in place of the two
   gpt-oss sections.**
   - **Gain:** each session can then reach the model's full 131,072 tokens instead of 8,192, and
     4 full sessions fit the memory left by the set (**estimate**, above).
   - **Why hold:** no attributed source measures this change on GB10. Unified KV pays a mask
     penalty with several sequences until #29510 lands, and that PR reports a P=1 regression.
   - **To check:** whether the server caps a unified slot at the trained 131,072, since `n_ctx_seq
     = n_ctx` when unified. b11669 also adds `--kv-unified-per-slot N` ("the shared KV pool is
     sized to n_parallel*N"), which may express this directly; read it before adopting.
   - **Risk:** no root. The rollback restores the preset's sections.
   - It is a preset change, which spike-model-engines owns.
3. **`--cache-ram 0` on the agent section, until #27624 lands.**
   - **Gain:** it removes #27148's cross-conversation restore risk under concurrent load. The cost
     is losing RAM-backed prompt caching.
   - **Why hold:** a primary bug report with no measurement on GB10 and no measured cost.
   - **Rollback:** remove the flag.
4. **SGLang `v0.5.22-cu130` and TensorRT-LLM `1.3.0rc13`.** Both are published images that serve
   gpt-oss-120b MXFP4 on this class, but no source measures either against llama.cpp on GB10.
   Neither lists Gemma 4, so either would need a second engine for vision and audio.
5. **vLLM v0.32.0.** It has only lead figures on GB10, and an open sm_121 issue. The architect
   keeps it down unless a finding favours it (Pauses, 2), and none does.

**Skip**

6. **Ollama and LM Studio:** neither names the llama.cpp build it embeds.
